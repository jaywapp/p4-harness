# 토큰을 덜 쓰는 Perforce 하네스

이 하네스의 아이디어는 **반복적인 P4 확인과 출력 정리는 코드가 맡고, 에이전트는 필요한 소스와 판단에 집중하게 하는 것**입니다. Claude Code와 Codex가 같은 CLI·규칙·상태를 사용합니다. 특정 엔진이나 빌드 도구는 전제하지 않습니다.

## p4.exe가 있는데 Python이 필요한 이유

실제 checkout·CL·파일 조회·shelf는 설치된 `p4`/`p4.exe`가 수행합니다. P4V도 그대로 사용합니다. Python 코어는 그 위에서 작업 범위·소유권·검증 기록을 확인하고 결과를 정리합니다. 별도 P4 구현이나 모델 API는 없습니다.

단순히 `p4 edit`을 한 번 호출하는 용도라면 Python 래퍼의 이점은 작습니다. 의미가 생기는 부분은 여러 명령으로 확인한 상태를 일관된 규칙으로 검사하고, 수백 줄의 목록이나 로그를 필요한 결과로 바꾸는 일입니다. 파일 해시 계산, JSON 비교, 로그 선별에는 모델 토큰을 쓰지 않습니다. 에이전트가 받는 응답에는 토큰이 들어가며, 기존 파일의 코드 리뷰까지 생략할 수 있는 것은 아닙니다.

기대효과는 반복적인 상태 해석·로그 읽기·인계 설명을 줄이고, 같은 CL에서 두 제품이 일관되게 작업하는 것입니다. 대신 Python 설치·하네스 유지보수와 P4 조회·해시 계산 비용이 추가됩니다. 작은 작업에서는 설정 비용이 절약분보다 클 수 있습니다. 실제 토큰·비용·작업시간 절감률은 아직 측정하지 않았습니다.

## 제안과 이번 반영 범위

| 아이디어 | 반영 방식 | 기대효과와 경계 |
|---|---|---|
| 짧은 P4 결과 | `collect`, `changes`의 기본 요약·페이지·`--full` | 경로/action과 총계부터 읽음. 전체 manifest는 보존 |
| 성공은 짧게, 실패는 원인 주변 | `verify`의 성공 메타데이터, 실패 로그 선별, 원본 경로 | 반복 빌드 로그를 대화로 가져오는 양을 줄임. 선별은 휴리스틱 |
| 이전 상태 이후 변경만 조회 | `changes --since <snapshot_id>` | 변하지 않은 파일 목록의 반복 전달을 줄임. 파일 단위 비교이며 코드 diff는 별도 |
| 프로젝트 탐색 지도 | 설치 시 `project-map.md` 틀 생성, 재설치 시 사용자 내용 보존 | 자주 찾는 진입점·관련 검증을 바로 찾도록 함. 자동 분석·자동 갱신은 없음 |
| 규칙을 필요할 때 읽기 | 필수 규칙과 짧은 skill, 별도 `workflows.md` | 상세 복구·리뷰 설명을 매번 읽지 않도록 안내. 필수 보호 규칙은 공통 계약에 유지 |
| 짧은 인계 자료 | `context`에 목표·범위·CL·현재 검증·인계 메모 결합 | 전체 대화 복사 대신 현재 작업에서 이어감. 메모는 작성자가 남김 |
| 기계적인 작업 묶기 | `verify --required`; 기존 `prepare FILE ...` 재사용 | 검증마다 모델이 다음 명령을 결정하는 왕복을 줄임. 검증 자체는 그대로 실행 |
| 중복 에이전트 작업 줄이기 | 공통 규칙에 단일 에이전트 기본, 추가 검토 목적 명시 | 두 제품이 같은 탐색·로그 읽기를 반복하는 일을 줄임. 자동 모델 선택·분업 기능은 없음 |

이는 프롬프트를 짧게 써 달라는 권고에만 의존하지 않습니다. 출력 선별과 상태 비교는 공통 Python 코어가 처리하고, 문서 탐색·인계 메모·추가 리뷰의 필요성은 작업 규칙으로 안내합니다. Claude의 공식 비용 가이드도 로그 전처리와 필요한 지식만 불러오는 방식을 설명합니다. Codex skill은 이름·설명으로 먼저 탐색하고 필요할 때 본문을 읽는 구조입니다. [Claude 비용 가이드](https://code.claude.com/docs/en/costs), [Codex skills](https://developers.openai.com/codex/skills).

## 1. 기본 응답과 전체 증거를 분리

아래에서 `p4h`는 패키지 설치 시 명령이거나 `python /path/to/p4h.py --workspace <P4-root>`의 약칭입니다. 전역 `--workspace`는 subcommand 앞에 둡니다.

```text
p4h collect
p4h changes --limit 10 --offset 10
p4h changes --full
```

`collect`는 예약된 새 파일을 작업 CL에 add하고 최신 snapshot을 만듭니다. 기본 응답에는 task·CL·snapshot ID·전체 파일 수·action별 총계·최대 10개 파일의 경로/action·전체 manifest 경로가 있습니다. `changes`는 새 파일을 add하지 않고 현재 상태를 검사합니다.

`page.total`은 전체 파일 수, `shown`은 이번에 표시한 수입니다. `next_offset`이 있으면 다음 페이지를 조회합니다. `truncated: true`이면 응답이 전체 목록을 포함하지 않습니다. 마지막 페이지라도 앞 페이지를 제외했으므로 true일 수 있습니다. `--limit`은 1~200, `--offset`은 0 이상입니다. 모든 페이지에서 action 총계는 전체 파일 기준입니다.

삭제·이동 등 검토해야 할 action을 첫 페이지만 보고 건너뛰지 마세요. 페이지를 이어 읽거나 `--full`을 사용합니다. 페이지 사이 snapshot ID가 바뀌면 파일 순서도 바뀔 수 있으므로 새로운 snapshot에서 검토 범위를 다시 확인합니다. 요약은 상세 증거로 들어가는 입구입니다.

전체 manifest는 `.p4-harness/state/manifests/<snapshot_id>.json`에 저장하며 파일 경로·depot·action·type·have revision·내용 해시를 유지합니다. 요약 응답에서 빠진 필드가 디스크에서 삭제되지는 않습니다.

## 2. 성공 로그는 생략하고 실패 원인 주변만 선별

```text
p4h verify unit
p4h verify unit --full
p4h verify --required
```

성공 기본 출력은 검증 이름·상태·종료 코드·snapshot ID·로그 경로입니다. 성공 로그를 대화에 붙이지 않습니다. 실패·timeout·stale에는 상태 메시지와 진단 발췌를 추가합니다. 종료 코드와 실행 전후 snapshot이 성공 여부를 결정하며, 로그의 `error` 유무로 통과를 판정하지 않습니다.

실패 발췌의 현재 한도는 다음과 같습니다.

- 원본 앞부분 최대 4 MiB에서 `error`, `failed`, `exception`, `traceback` 등의 행을 탐색합니다.
- 먼저 발견한 진단 주변을 최대 24행·3,000자까지 반환합니다. 긴 행은 진단 근처를 중심으로 줄이고, 동일 진단 앵커의 반복 선택을 줄입니다.
- 찾지 못하면 원본 끝 8 KiB 중 마지막 최대 24행을 사용합니다. 비영어 로그나 도구 고유 형식은 이 경로를 사용할 수 있습니다.
- `selection`, `scanned_bytes`, `log_bytes`, `matched_lines_in_scan`, `truncated`로 선택 방식과 생략 여부를 알립니다. 일치 행 수는 실제 오류 개수가 아닙니다.

원인이 중간에 있거나 앞부분에 부수적인 진단이 많으면 원하는 내용이 빠질 수 있습니다. 발췌가 불충분하면 반환된 `log` 파일을 필요한 구간부터 읽습니다. **원본 로그는 상태와 무관하게 전부 보관합니다.** `--full`은 전체 검증 메타데이터와 기존 방식의 마지막 약 4,000바이트를 반환하며, 로그 파일 전체를 출력하는 옵션은 아닙니다. 로그 정리·삭제는 자동 수행하지 않습니다.

`verify --required`는 `required_checks`의 순서로 실행하며 실패·timeout·stale에서 멈추고 `not_run`에 남은 검증을 표시합니다. 검증 사이 snapshot이 바뀌어도 전체 상태를 stale로 보고합니다. 이때 각 항목의 passed는 해당 snapshot에서의 개별 결과이며 전체 통과가 아닙니다. 필수 목록이 비어 있으면 `not_configured`입니다. 이 상태는 exit 0이지만 검증 통과를 의미하지 않습니다. `finish`는 별도 명령이고 최신 상태를 다시 확인합니다.

## 3. 이전 snapshot 이후 바뀐 파일만 읽기

처음 검토한 `collect`/`changes`의 `snapshot_id`를 기록하고, 추가 편집 후 비교합니다. 새 예약 파일을 작성했다면 먼저 collect로 add해야 합니다.

```text
p4h changes --since <이전에-받은-64자리-snapshot_id>
p4h changes --since <이전에-받은-64자리-snapshot_id> --full
```

| 비교 결과 | 의미 |
|---|---|
| `introduced` | 이전 manifest에 없던 파일 항목 |
| `updated` | 기존 항목의 내용 해시·action·type·have revision 등 변화 |
| `removed` | 이전 manifest에 있었으나 현재 manifest에서는 빠진 항목 |
| `unchanged` | 항목이 동일함. 기본 변경 목록에서는 생략하고 수만 표시 |

이 분류는 P4 action과 다릅니다. 예를 들어 기존 tracked 파일을 새로 checkout하면 비교상 introduced일 수 있으며 P4 action은 edit입니다. removed도 파일의 실제 삭제와 동일한 뜻이 아닙니다. `--full` 비교는 변경 항목의 before/after 메타데이터를 보여줍니다.

**파일 단위 선택 기능이며 텍스트 diff 기능은 아닙니다.** 이전 snapshot의 파일 본문을 저장하지 않으므로 이전 로컬 편집 대비 줄 단위 diff를 제공하지 않습니다. 관련 코드와 파일별 `p4 diff -du <file>`을 읽고, 새 파일은 전체 내용, 삭제·이동은 참조 영향을 검토합니다.

비교는 같은 task·CL·환경·have baseline에 한정합니다. snapshot ID 형식과 저장된 manifest의 해시를 검증합니다. 다른 작업의 기록이나 손상된 manifest를 비교 기준으로 사용하지 않습니다.

매 조회마다 실제 P4 환경·CL·have·opened·offline 변경을 확인하고 현재 파일을 해시합니다. 저장된 snapshot은 비교 자료이며 편집 허가 캐시가 아닙니다. 이전에 확인한 다른 CL·lock 상태를 근거로 checkout 검사를 생략하지 않습니다. 따라서 이 기능의 목표는 모델이 읽는 양을 줄이는 것이며 P4 호출 횟수·서버 부하 감소를 보장하지 않습니다.

## 4. 프로젝트 지도와 필요한 규칙만 로딩

설치된 `.p4-harness/project-map.md`에는 경로·역할·진입점·관련 check profile만 짧게 기록합니다. 예를 들어 실제 확인한 파서 구현 경로와 관련 테스트 경로를 함께 남깁니다. 확인 날짜나 revision을 붙이고, 해당 영역을 읽을 때 현재 코드와 대조합니다. 전체 디렉터리 목록·코드 본문·작업 로그를 넣지 않습니다.

프로젝트 지도는 처음 설치할 때 빈 틀로 만들며 재설치로 덮어쓰지 않습니다. 자동 생성한 지도를 사실로 가정하지도 않습니다. 관리자가 확인한 내용으로 채우고 필요한 영역만 읽는 운영 방식입니다.

공통 `rules.md`에는 범위·소유권·checkout·검증·보존 등 항상 지켜야 할 계약을 남깁니다. 상세 리뷰·복구는 `workflows.md`로 분리하고 공통 skill은 해당 파일을 필요할 때 읽도록 안내합니다. Claude와 Codex의 skill 본문은 같습니다. 이미 읽은 규칙을 반복 조회하지 않도록 안내하지만, 실제 모델이 지시를 따르는 정도와 제품의 컨텍스트 로딩 비용은 별도 측정 대상입니다.

## 5. 대화 대신 현재 작업을 인계

```text
p4h handoff --to codex --note "빈 입력 처리는 유지. 경계값 테스트가 남음. unit 확인 후 완료."
p4h context
p4h context --full
```

받는 쪽은 `context`로 목표·범위·소유자·CL·인계 메모·현재 변경 요약·필수 검증 상태를 한 번에 확인합니다. 파일 내용이나 check 설정이 바뀌었다면 저장된 passed를 현재도 유효한 것으로 보여주지 않고 stale로 표시합니다. 메모는 이전 작성자가 결정·남은 문제·다음 행동 중심으로 작성합니다. 자동 대화 요약 모델은 사용하지 않습니다.

기본 context는 목표·pause 메모·인계 메모를 각각 최대 500자, scope를 최대 10개로 표시하고 `truncated_fields`를 반환합니다. 생략된 내용은 `--full` 또는 `task_record` 경로에서 확인합니다. 변경 목록에는 동일한 페이지 옵션이 적용됩니다.

`context`는 소스·CL·소유권을 바꾸지 않는 조회이며, 최신 manifest 증거는 디스크에 기록합니다. 미등록 새 파일이나 환경 변화가 있으면 현재 상태 조회도 거절할 수 있습니다. 예약 후 작성한 새 파일은 현재 owner가 먼저 `collect`하고, 연결 문제 등으로 막혔다면 `status`로 저장된 메모를 확인합니다. `status` 자체는 실시간 검증 결과가 아닙니다.

## 6. 왕복과 중복 작업 줄이기

여러 파일을 shell에서 수정한다면 `prepare file1 file2 ...`로 한 번에 준비하고 편집 묶음 뒤 collect합니다. 필요한 필수 검증은 `verify --required`로 순서대로 실행합니다. 내부의 검증 전후 상태 확인은 유지하므로 모델 왕복 감소와 실제 명령 실행량 감소는 구분해야 합니다.

두 제품이 모두 같은 탐색을 반복하는 방식은 기본 흐름으로 두지 않습니다. 일상 수정은 한 에이전트가 진행하고, 다른 에이전트가 필요하면 보안 경계 검토·별도 테스트 설계 등 구체적인 목적과 필요한 파일만 인계합니다. 이를 강제하는 자동 분업이나 저가 모델 라우터는 구현하지 않았습니다. 한 물리 workspace에서 두 작성자를 동시에 실행하는 제한도 그대로입니다.

## 효과를 확인하는 방법

동일한 작업·scope·검증 기준에서 기존 상세 출력 방식과 새 기본 출력을 비교합니다.

| 지표 | 기록할 내용 |
|---|---|
| 모델 사용량 | Claude/Codex 전체 입력·출력 토큰, 캐시된 입력 별도, 추가 에이전트 사용량 포함 |
| 응답 크기 | collect/changes/context/verify 응답 바이트, 전체 로그 바이트 |
| 왕복 | 도구 호출·상세 확장·재검증·재시도 횟수 |
| 품질 | 누락한 변경·잘못된 성공 표시·리뷰 수정·최종 required check 결과 |
| 운영 비용 | P4 호출 시간·해시 계산 시간·설치/지도 관리 시간 |

토큰 수와 청구 비용, P4 호출 수는 서로 다른 지표입니다. 캐시 할인이나 제품별 과금 방식도 분리해 기록합니다. 출력이 줄어도 추가 조회·추론·재시도가 늘면 전체 절감은 작아지거나 없어질 수 있습니다.

자동 테스트는 200개 파일의 합성 manifest에서 기본 응답이 전체 JSON보다 작은지 **직렬화 바이트**로 확인합니다. 이는 실제 tokenizer·세션·청구 비용 측정이 아닙니다. 실제 임시 P4 서버에서는 삭제 action 총계, 파일 내용 변화, 다른 CL·have 변화 거절, 검증 stale, 실패 로그 원본 보존, 인계 조회를 확인합니다. 상세 범위는 [testing.md](testing.md)를 참고하세요.

## 0.2 업그레이드와 호환성

0.2부터 `collect`, `changes`, `verify`의 기본 JSON은 요약형입니다. 기존 자동화가 full manifest를 파싱했다면 `collect --full` / `changes --full`을 사용합니다. `verify PROFILE --full`은 기존 메타데이터와 `output_tail`을 유지하며 `check`와 실패 진단이 추가될 수 있습니다. `--since`를 지정하면 요약/전체 모두 비교 결과 schema가 됩니다. 페이지 옵션은 `--full`에서 출력 제한에 사용하지 않습니다.

상태/config schema 버전은 그대로이며 기존 snapshot도 비교할 수 있습니다. 저장소 또는 패키지를 업데이트한 뒤 기존 client 설정으로 `install --dry-run`, `install`을 다시 실행해 규칙·skill·상세 workflow를 갱신합니다. 바뀌는 기존 파일은 백업하며 project map은 보존합니다. read-only 구성 파일은 기존 절차의 구성 CL에서 준비하고, provider의 훅 로딩/신뢰 확인은 [설치 확인 절차](testing.md#실제-제품에서-설치-확인)를 따릅니다.
